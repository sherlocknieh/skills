# <项目名> 的 Agent 规则

## 使用说明（自迭代协议）

本文件由通用示例模板原样复制而来，占位符不是待填空，而是待办清单和弹窗触发点：

- `<...>` 与 `[待定]` 在会话中被读到时，按「全局规则」的 [询问]/[待定] 协议弹窗问用户，答案直接写回本文件对应处。
- 每确认一处就填掉一处；未确认的保持原样留给后续会话，不要预填猜测内容，也不要删掉占位符。
- 必须保留：`开发流程`（含自动检验前后的询问）、`实现约定 → 调试约定`、`记忆落点`、`自动提交`。
- 逐文件的职责、命令清单、站点特性等细节写在 `docs/`，本文件只放流程与约定；项目事实补齐后，本节可精简成一行指针。

## 全局规则

AGENTS.md 是必须遵守的项目规则文档。
一份动态迭代文档, 随着开发者与 Agent 的对话不断更新; 每次对话中发现的新约定直接改写对应条目, 不留变更史。

遇到标记了[询问]/[待定]的操作, 必须先弹出对话框询问用户:

- [询问]操作可询问: "本次确定/本次取消/总是确定/总是取消/用户补充[...]" 之类的选项;
- [待定]内容可询问: "自行扫描/用户补充[...]/本次忽略" 之类的选项;

根据用户的选择和回应更新本文档内容后, 才能继续执行后续操作。

- [询问]操作根据用户的选择, 修改为 [必须]/[跳过] (或维持 [询问])。
- [待定]内容根据用户的选择, 修改为具体内容 (或维持 [待定])。

## 开发流程

- 用户: 提出需求
  - [询问]如果用户只发了截图, 没有提供描述, 弹出对话框协助用户补充完整。
- Agent: 按[定位流程](#定位流程文档优先)先查文档、再查代码, 理解当前实现, 给出实现方案
  - 方案开头写明「已查阅: <文档>; 结论: …」, 文档已覆盖的部分不再重复读代码
- Agent: [询问]用户选择/确认/补充方案
- Agent: 动手实现
  - 代码约定: 见 [实现约定](#实现约定)
  - 调试约定: 见 [调试约定](#调试约定)
  - 注释约定: 见 [实现约定](#实现约定)
- Agent: 只跑构建、测试、类型检查等静态或本地命令
- [询问]Agent: 启动浏览器 / 打开站点 / 对已共享页面做 reload、点击、输入等真机验证
- 用户: 手动检验实现效果（简单的视觉变化由用户自己看）
- Agent: [询问]更新文档
  - logic 文档: 本次了解到的机制、根因、链路
  - features 文档: 本次实现的需求与实现方式
- Agent: 按[自动提交](#自动提交)处理提交
  - 是否自动提交、是否自动发布以本节已确认的规则为准, 未确认时为[询问]

## 定位流程（文档优先）

任何需求、缺陷或「为什么这样」的问题, 先走文档, 再打开代码; 目的是复用已有结论, 避免重复阅读。

0. **读本文件**: 会话的第一条工具调用先读 `AGENTS.md`, 再开始任何检索; 不要在读完代码后才补读。
1. **提词**: 从用户原话里取 1–3 个关键词(界面名、控件名、现象), 到[关键词索引](docs/keyword-index.md)搜索。
2. **读文档**: 命中后先读索引指向的 logic/features 文档; 完全没命中就先读[代码地图](docs/architecture.md)与[编码约定](docs/conventions.md)。
3. **标注结论**: 回复或方案里先写「已查阅: <文档>; 结论: …」, 再列要改的文件。文档已覆盖的部分不再重复读代码; 只有文档缺细节、与代码不符、或需要确认行号时才打开源码。
4. **补文档**: 文档缺失、过期, 或答案只存在于本轮阅读中时, 按[记忆落点](#记忆落点自动执行不需要用户提醒)在同一个任务里补齐并登记索引, 再改代码或提交。
5. **留锚点**: 改动核心机制时, 在代码注释里写明对应文档路径, 让下一次的代码搜索也能回到文档。

自检: 本轮的结论如果全部来自重新读代码、没有引用任何文档, 视为流程未执行; 要么找到对应文档, 要么本轮补齐。

## 实现约定

### 注释约定

- UI类注释: 适应人类描述界面的习惯，把**用户原话/惯用名称**以注释方式置于代码附近，便于搜索定位, 例如:

```html
<!-- [跳转条/搜索条/划词条]: -->
```

- 函数/类/组件的注释: 顶部注释写明它被哪些地方依赖、依赖哪些信息、作用是什么。
- 流程/机制/链路的注释: 每个步骤上方一句话概述作用, 便于快速理解链路。
- 只写目的与约束（为什么这样做、改版时注意什么），不写步骤复述，不写变更史。

### 代码约定

- <项目特有的编码约定: 语言/风格/框架/目录边界/禁止事项>
- 取最小完整集: 能改现有代码就不新增实体; 新增前说明为什么现有承载点不合适。
- 同一功能只保留一处实现; 每条事实只在一处文档记录。

### 调试约定

- **不要自行启动浏览器进行调试，必须先问用户。**
- 改完代码只用构建、测试、类型检查、lint 等命令验证；启动浏览器、打开目标站点、对已共享页面做 reload / 点击 / 输入 / 截图等操作，都必须先弹窗询问。
- 简单的视觉变化交给用户自己看，不主动接管用户的浏览器会话。
- 用户同意调试后，按 `docs/development.md` 记录的方式操作；调试产物不覆盖要提交的产物。

### 记忆落点（自动执行，不需要用户提醒）

| 发生了什么 | 写到哪里 | 判据 |
| --- | --- | --- |
| 用户用现象描述界面 | `docs/keyword-index.md` | 说法 → 文件 + 锚点 |
| 新需求 | `docs/features/` | 日期 / 需求 / 实现要点与文件 |
| 机制与根因 | `docs/logic/` | 受影响的机制、根因与修正后的现状逻辑 |
| 目录、命令、数据模型变化 | 本文件与 `docs/architecture.md` | 结构变化后立即同步 |
| 架构取舍 | `docs/decisions/NNNN-<主题>.md` | 背景 / 选项 / 结论 / 影响 |
| 已知坑与规避方式 | `docs/known-issues.md` | 现象 / 原因 / 规避 |

- 只记现状：行为改变直接改写原条目，不留历史变更；功能删减直接删掉对应描述。
- 同一对象的新说法并入同一条「用户可能说」列，用 ` / ` 分隔，保持一份不重复的对照表。
- 缺陷结论留在 `logic/`，不写进 features；没有篇目就新建并在该目录 `index.md` 登记。
- 代码与文档在同一轮完成，不攒到以后。

## 自动提交

- 提交: 改完代码 [询问]是否自动提交; 确认后在此写明「每轮对话后自行提交（除非只有单处微小细节改动）」。
- 版本号: <格式与生成方式> 或 [待定]。
- 发布: 改完代码 [询问]是否自动发布; 仓库有发布脚本时走发布脚本, 不先单独 `git commit`。
- 发现会话外改动时先弹框询问如何提交，选项必须包含「直接提交」。

## 其它注意事项

- **代码改动**：遵循仓库既有规范，取最小完整集。
- **概念取舍**：先判断是同一件事的两种形态还是两件事，再决定统一还是分开；差异尽量落在数据、配置或适配器上。
- **克制**：加代码前先想能不能让代码变少；每行都要有存在理由。
- **UI**：能用图标就别用文字，能用系统功能就别自定义实现。
- **注释**：每块代码上方一句目的性描述（做什么、手段、上下游），写现状不写变更史。
- **不要自行打开浏览器调试**：改完代码只用测试、构建、类型检查验证；启动浏览器，或对已共享页面做 reload、点击、输入等操作，都必须先问我。简单的视觉变化我自己看就行。
