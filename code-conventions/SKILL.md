# 代码项目工作约定

`~/.config/opencode/AGENTS.md` 里只有压缩版的一句话规则，这里是完整判断依据。动手前先读仓库既有规范（命名、目录、构建与发布脚本），改动取最小完整集。

## 如无必要，勿增实体

能改现有代码，就别新增模块。在已存在的实体上修改，比新增一个实体更容易保持简洁和可维护。

加代码要克制。每行都要有存在的理由，先想能不能让代码变少或结构变简单，而不是先加上再说。

## 复用优先检查

新功能先找现成的承载点，别急着新建页面、入口、组件或服务。

先读项目说明和目录结构，盘点现有的页面/路由、入口、宿主组件、composable 与 service，找出职责最接近、生命周期也匹配的那个。

如果新功能和现有页面属于同一类任务，就扩展那个页面、复用已有流程。比如图片获取、预览、识别、通知，先看现有上传/识别页面能不能多一种输入方式，而不是直接新建页面。只有现有承载点在生命周期、权限、交互或职责上确实不合适时，才新增实体，并说明为什么不复用。

提方案前至少比较一次「复用现有承载点」和「新增承载点」，优先选改动更小、能复用既有流程的方案。

## 先统一概念，再统一实现

先判断这是同一件事的两种形态，还是两件事。

依据不是长得像不像，而是生命周期、所有权、失败模式和输出契约。输出契约一致的部分只该有一份实现，输入与呈现可以不同。

差异尽量落在数据、配置或适配器上。只能靠条件分支或两处复制承载的差异，说明概念还没统一。

但不要为了合并而合并。需要引入大量参数、回调或可选字段才能统一时，它们本来就不是同一件事，分开更便宜。

用延展性检验设计：再加一种形态要改几处？删掉一种会不会牵连另一种？这比看当前代码量可靠。

一致性要由结构保证。靠补齐占位或人工同步维持的一致，下一个变体出现时就会散。

「统一/合并/简化/优化」这类词，先说明你选了哪种解释再动手。事实靠实验确认，偏好靠用户给定，两者不要互相冒充。

## 极简主义 UI 设计

能用图标表示的，就用图标表示，而不是用文字描述；能复用系统功能的，就复用系统功能，而不是自定义实现。

## 注释要求

每条动作/每块代码上方一句话说明在做什么。要用目的性描述，不要用步骤描述。使开发者不看代码，只看注释就能理解代码的目的、手段和结果。

注释要包含上下游信息，能从注释里知道代码的调用源和去向。

改动代码时同步重写受影响的注释，保留最初动机和最新现状，不写变更史。读者从注释里看不出这段代码改过几次，就好像它一开始就是这么写的。

- 反例：「扫码面板: 进入后可选打开相机或上传图片, 不再单列上传入口」
- 正例：「扫码面板: 进入后可选打开相机或上传图片」
